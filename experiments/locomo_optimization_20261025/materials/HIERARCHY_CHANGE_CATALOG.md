# L3–L5 加入后的实现变更目录与实例

日期：2026-10-25。用途：为项目 GitHub PR 的技术说明提供可核查材料。本文件仅整理本地已有实现，不重新调用模型，不修改记忆库、评测结果或生产代码。最终成绩以完成两题缓存修正后的报告为准。

## 1. 贡献的准确定位

TiMEM/AML 原有的分层记忆思想、记忆写入和长期整合能力，不应表述为本轮新增发明。本轮在本地 LoCoMo 实验链上落实的是：**使分层摘要的时间来源更明确，使高层摘要导航到可追溯的低层事实，并以受约束的方式选择和呈现证据。**

本轮主要修改本地冻结快照、SQLite 检索索引和评测程序。不能等同于已经修改太忆空间云端原生服务或验证其线上召回成绩。现有脚本还有实验目录的绝对路径；进入上游仓库时，应把这些路径改成配置，并按本目录所列模块边界迁移。

必须区分以下对象：

| 对象 | 本轮实际变化 | 不是本轮完成的内容 |
|---|---|---|
| 记忆存储 | 时间字段、注释来源、规范化事实 ID、父子继承关系 | 没有普遍恢复所有 L1 原始逐字对话 |
| 高层摘要 | 保留摘要作为检索别名和导航入口，连接后代事实 | 没有证明所有摘要都完全保真或所有链接都具有语义蕴含 |
| 证据选择 | 去重、中心窗口、保护主要证据、有限候选交换 | 没有强制每题都输出五层摘要 |
| 评测 | 同库对照、完整输入审计、交换校验、错误回退 | 不是无记忆消融，也不是独立未见测试集验证 |

以下中文均为已保存英文记录的简译；标为“机制示意”的片段只解释程序行为，不冒充真实答题记录。

## 2. 本地五层快照：把原始观察整理成可复现实验输入

### 实现

从冻结的 5,882 条 L0 turn、10 段对话构建 1,236 个节点：L1 399、L2 272、L3 272、L4 207、L5 86。

- L1：同一原始会话内，最多 20 条 turn 的分段摘要。
- L2：一次会话的摘要。
- L3：一天的汇总。
- L4：月内的周范围汇总。
- L5：一个月的汇总。

节点保存对话归属、覆盖区间、子节点引用和生成内容。这是用于测试的分层快照构建，不把“生成了日、周、月摘要”写成新的记忆架构发明。

### 具体落点

- `locomo_space_l1_l5_20261024/build_hierarchy.py::plan()`：分层分组和节点 ID。
- `locomo_space_l1_l5_20261024/build_hierarchy.py::prompt_for()`：各层摘要输入。
- `locomo_space_l1_l5_20261024/generated_memories.json`、`hierarchy_plan.json`：冻结数据。

### 发现的问题和边界

第一版直接用五层摘要做检索和证据正文，摘要可能重复，也可能缺少细节。该阶段另有全部证据被错误限制为 8,000 字符的问题，不能把该阶段的低分直接归因于高层记忆本身无效。

## 3. 上层 W0：把归档范围与事实自己的时间分开

### 修改前后

修改前，高层节点有覆盖区间，摘要内部也可能带观察日期，但各种时间没有统一拆成可核验字段。修改后，565 个 L3–L5 节点采用 `upper-w0-fact-time-v2`；原有 671 个 L1/L2 节点 JSON 保留。

```text
window.start / window.end：该日、周、月汇总覆盖的范围，只用于归档。
fact_units[].observed_at：说出这条事实的那次会话时间。
annotations[].raw_phrase：原文中的时间词。
annotations[].precision：天、月、年、周、周末等粒度。
annotations[].normalized_value 或 anchored_value：日历值或相对锚点。
annotations[].source_id / span：来源编号和原文字符位置。
```

### 真实实例：Melanie 的陶盘

L5 节点 `fb0c8434-c843-5fce-a17e-b7c197d601be` 覆盖 2023-08-14 至 2023-08-28。它的一条事实为：

> 2023-08-25，Melanie 说，她昨天在陶艺课上做了这个盘子。

新结构保存的关键字段：

```json
{
  "window": {"start": "2023-08-14T06:24:00+00:00", "end": "2023-08-28T07:19:00+00:00", "purpose": "aggregation only"},
  "fact_observed_at": "2023-08-25T05:33:00+00:00",
  "raw_phrase": "yesterday",
  "source_id": "src:ae0f239c1037e7d0486ad4b4b9c7cd0f",
  "span": [33, 42],
  "precision": "day",
  "normalized_value": "2023-08-24"
}
```

这里的 `fact_observed_at` 是为阅读方便对实际嵌套字段所作的展平展示。实际字段位于 `fact_units[].observed_at` 与注释的 `data` 内。

实质改变是：**“昨天”从 8 月 25 日换算，月摘要覆盖到 8 月 28 日不会成为时间锚点。** 不能据此虚构旧系统实际曾把这件事算成 8 月 27 日；已核实的是新表示明确排除了这种字段混用。

### 时间精度和短语边界

- `last week` 保留“相对于观察日期的上一周”，不擅自写成某一天。
- `last weekend` 单独保留周末粒度。
- 优先最长短语、整词匹配，避免把 `last week` 绑定进 `last weekend`，或把 `yesterday` 绑定进 `day before yesterday`。
- 只在构建阶段读 L0 核对短时间词和字符位置；答题阶段不重新读取 L0。
- “同一观察时间 + 相同原文短语”是可核验的时间注释依据，但不被宣称为唯一事件对应证明。元数据保留了该限制。

### 代码

- `locomo_upper_w0_20261024/upper_w0.py::eligible_phrases()`：短语边界和最长匹配。
- 同文件 `split_units()`、`prepare_store()`：事实拆分、事实观察日期、来源校验、注释持久化。
- 同文件 `render()`：按事实自己的观察时间输出，沿用 W0 注释。

## 4. 恢复主证据预算，明确摘要身份

第一版将 8,000 字符当作整份证据上限，861 题中 821 题触及限制。修复后复用原 W0 的 `format_memories`：主证据预算为 117,760 token 再扣查询；8,000 字符只限制新增时间注释。

机制示意：检索选中 A、B、C 三段内容时，不能因为新增注释的上限而把整个正文只留下 A。

新渲染还显式使用：

```text
Derived memory summary:
[2023-08-25T05:33:00+00:00] memory: Melanie said ... yesterday ...

Temporal calendar annotations ...
- raw_phrase="yesterday"; calendar_value=2023-08-24; precision=day; ...
```

这样不会把摘要改写伪装成原话逐字引用。上层 W0 的主证据预算修复和时间存储改造同时进入全量，缺少预算单独修复的全量对照，不能精确拆分两者的分数贡献。

代码：`upper_w0.py::render()`；后续统一到 `grounded.py::Retriever.render()`。

## 5. 统一事实库和确定性继承：高层提供目录，低层提供正文

### 修改前后

修改前，同一事实会被不同层重复改写，并可能多次作为正文入证据。修改后，从 L1/L2 正文构建 **7,157 条规范化事实**，按“对话 + 观察时间 + 规范化正文”去重，保留多份来源。

- L2 同时继承其 L1 中更详细、但 L2 摘要省略的事实。
- L3–L5 继承后代事实 ID，不重新让模型改写这些事实。
- 高层旧摘要保留，作为检索导航文字。
- 高层摘要单元仅能连接实际后代事实；无合格连接的摘要单元不直接作为事实输出。
- 最终正文和时间来自同一份低层事实库，父摘要覆盖时间不覆盖事实观察日期。

### 真实实例：三款游戏保留原有两份来源

事实 `fact:cf9cd94d0ebfd3e0b5d3ad52a44e7d27`：

> Assistant 推荐 Switch 上的 Zelda BOTW，并推荐令人放松的 Animal Crossing: New Horizons。

它的 `origins` 同时保存：

```text
L1 node = 8f2a68cc-3730-5e77-b57c-554bde126ad2
L2 node = 5d00037f-349d-5657-8eb5-d036d531d2e3
observed_at = 2023-08-18T16:52:00+00:00
```

两层说的是同一事实时，正文只输出一次；高层可以通过不同摘要说法找到它，不再逐层输出同一句话。

### 实现和限制

- `locomo_hierarchy_grounded_20261024/grounded.py::construct()`：规范化事实、`origins`、递归 `inherited()`、路由链接、FTS5 索引。
- `store.json`：事实、上下文分组、节点继承、原始导航路径。
- `index.sqlite`：底层事实和高层导航两种全文检索表，按对话隔离。
- 原有 16,950 个高层单元中 16,884 个有合格词面链接，66 个不直接输出。这是词面链接门槛，不是语义完全正确的证明。
- 规范化去重消除的是规范化文本相同，不保证所有同义改写都归并。

## 6. 以目标为中心保留上下文，修复目标没有进入证据的问题

`grounded.py::Retriever.window()` 使用目标附近各两条事实；目标在会话较后位置时，还保留开头两条。窗口限定同一观察时间。

机制示意：目标为会话第 10 条，旧 R1 拼装有时拿整个分组的前七条，最终没有第 10 条；正确窗口围绕第 10 条取上下文，而不是无条件截取第 1–7 条。早期 R1 曾退回错误拼装，后续基线恢复到此函数。

### 真实实例：命中的是回应，答案在邻居里

题 `conv-48#q0054`：Jolene 给 Deborah 推荐哪些游戏？

- 低层证据没有三款具体名称，答题输出 “Video games.”。
- 高层导航找到 2023-08-18 会话；导航中心 `fact:3d6b9233a6410efff4a0a39a614f1602` 本身是收到推荐后的回应。
- 同窗口中的 `fact:cf9cd94d0ebfd3e0b5d3ad52a44e7d27` 提供 Zelda 和 Animal Crossing。
- 邻近 `fact:3f4f32d2b354241bfdf0d6170e68c010` 补充 Overcooked 2。
- 联合组输出三款游戏；固定证据的两次记录都呈现这一差异。

这证明了该历史样例中的有用变化，不把每个后续版本都写成同样解决了该题。来源：`locomo_hierarchy_grounded_20261024/HANDOFF_SCORE_AUDIT_20261024.md`。

## 7. 折叠重复高层路径，保留别名而不重复投票

同一事实可能同时被日、周、月摘要找到。R1 将“同一对话 + 相同目标事实集合”的路径折叠：**16,950 条原始路由变为 6,581 组规范化路由**。

机制示意：

```text
原：日摘要→事实 A，周摘要→事实 A，月摘要→事实 A。
新：规范路由→事实 A；aliases 保留三种说法；provenance_levels 保存 L3/L4/L5；independent_support=1。
```

最终 V2 候选生成按这些折叠后的 `aliases` 与查询词重合程度排序，不把同一条事实在三层出现当成三份独立证明。

代码：`locomo_hierarchy_relevance_r1_20261024/tools/build_routes.py::main()`，产物 `routes_r1.json`；最终使用入口是 `r13b_prepare.py::build_pools()`。

## 8. 有限补充、保护主要证据，以及低层对照组

最终 B/L/H 使用相同事实库和渲染器：

- B：原低层检索窗口。
- L：低层候选重排，提供最多 12 个低层候选。
- H：8 个低层候选，加最多 4 个高层路径候选；不足时用剩余低层候选补足。
- 最多 24 个证据窗口，前 20 个受保护，候选最多替换末尾 4 个窗口。
- 只对词面规则识别为组合、列表等的问题进行可选筛选；直接日期等 guard 问题保持 B。

### 为什么需要保护：真实干扰反例

题 `conv-42#q0168` 问 Joanna 来 Nate 家时 Nate 想做什么。B 和高层组都已有“看 Joanna 的电影，或者去公园”的正确事实；加入更多上下文的历史高层组却两次回答“尝椰奶冰淇淋”。多项事实同时变动，不能声称某一行是唯一原因，但该例说明“相关话题更多”不一定更好。

### V2 修复候选过早排除

旧候选构建曾把低层扫描到、尚未选入证据的事实也算“已经看过”，导致高层入口被排空。最终 `build_pools()` 中，H 的排除集合只包含 B 事实和 H 实际选中的 8 个低层候选；候选按相关程度进入，保持事实 ID 唯一。

代码：`locomo_hierarchy_relevance_r1_3b_20261024/r13b_prepare.py::build_pools()`；最终 `locomo_hierarchy_relevance_full_20261025/full_prepare.py::main()`。

## 9. 联合比较完整证据，执行受约束的等量交换

最终筛选器一次看到问题、完整受保护窗口、可换出的尾部窗口、候选事实。模型需同时说明候选提供的具体答案或推理连接，以及删除哪些窗口；最多 4 换 4。

### 具体修复

- 移除早期 `text[:420]`、`text[:160]` 等导致目标隐藏的截断；完整序列化事实正文。
- 提示过长时整项移除候选，不能在半句话或半个 JSON 中截断。最终全量没有实际触发候选缩减。
- 拒绝只删除不补充、未知编号、重复编号、删除保护窗口、数量不匹配和选中明确约束冲突的候选。
- 修复多删时的下标移动：旧代码按位置逐个 `pop()`，删 t2、t3、t4 可能留下 t3；新代码按固定标签一次过滤，再添加候选。
- 不再靠 `[:24]` 静默截掉最后一个候选；超限明确拒绝并回退。
- 失败保留 B，保存失败状态，不把网络错误解释成语义筛选结果。

## 11. 评测和可复现性改进

1. **同库对照**：B/L/H 共享 7,157 条事实和 W0 渲染，区分低层重排与高层导航候选的作用。旧 W0 包含原始对话检索，不将其称作纯 L1/L2 严格消融组。
2. **构建与答题分离**：构建阶段可核对 L0 短时间注释；运行期读取冻结事实库与索引，不把 gold、类别或历史正确性作为存储内容。guard 来自问题词面规则，不从数据集类别直接决定答案证据。
3. **过程留痕**：保存每题提示、提示 hash、证据、窗口与事实 ID、筛选计划、原始响应、重试和失败回退；manifest 保存代码与模板 hash。
4. **生产路径检查**：最终 814 个筛选任务终态的提示 hash 与当前请求一致；交换与实际证据一致；保护窗口未变化；guard 与失败回退等于 B。筛选任务数和包含重试的 API 尝试数分别报告。
5. **逐题配对结果**：报告转对、转错和 McNemar 检验，不只展示总分；将“证据改变”与“高层候选实际被选入”分别统计。
6. **缓存修正**：先前证据相同、问题不同会错误复用答案和正确标记。两题修复由主任务执行；最终 PR 应采用修复后的完整问题/模型输入绑定方式、局部重答结果和修订后的分数，不引用原有缓存分数作为最终值。

### 已核实、不会因两题修正改变的最新全量事实

- 完成 861 题，每组都有完整证据。
- H 相对 B 有 150 题证据文本变化。
- 其中 78 题真正选入高层路径找到的事实，共 101 个候选项；它们来自共享低层事实库，并实际进入最终证据。
- 78 题中 6 转对、1 转错，净 +5；另 72 题仅低层候选变化，4 转对、4 转错，净 0。
- 711 题证据相同，原保存答案与正确性也相同。
- 两道缓存问题的 B/L/H 证据各自完全相同，同样局部修正，组间净 +5 不受影响。
- 多跳与推理在当前比较中各少对 1 题，不能写成所有类别均提升。
- 整体提升没有达到统计显著；861 题已多轮参与开发，不能称为未见测试集。

绝对正确题数与分类百分比待两题重新答题、判分后以主报告定稿；本目录不提前人工猜测两题会对会错。
