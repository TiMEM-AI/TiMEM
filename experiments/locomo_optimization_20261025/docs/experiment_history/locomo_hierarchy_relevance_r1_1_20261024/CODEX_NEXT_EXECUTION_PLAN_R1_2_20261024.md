## 3. 必须先修正的三个测量问题

### 3.1 槽位饱和不等于答案覆盖

当前 `window_slots()` 主要保存实体名、关系词，以及 time/person/place/reason 这类类型标记。一旦 B 中出现过“某人”“recommend”“time”等字样，其他涉及新游戏名、新地点或同一事件正确日期的窗口就可能被判 `no_new_slot`。

替换条件也存在逻辑过严：`covered_slots` 已经包含全部已选窗口的槽位，因此 `victim_slots & covered_slots` 只要 victim 有任意槽位就成立，并不表示它拥有不可替代的答案支持。与此同时，`new_slots` 定义为去掉 covered 后的槽位，它与 victim 已覆盖槽位通常天然不相交，不能用这个交集有效衡量替换损失。

所以三种选择器的“0 接受”不是三个独立证据互相印证。规则选择器可能在入口已经排除了真正有价值的同类型答案；模型输入又有下述调用与截断问题。

### 3.2 筛选调用失败不能当作负判决

当前 `tools/p1_model_screen.py` 声明了 `KEY`，但 `client.post()` 没有传鉴权头。异常捕获重试后返回空数组，后续缺失 ID 被记为 unknown/不接受；没有保存状态码、错误、原始响应或实际模型名。

由此不能确认历史请求究竟返回了鉴权错误、其他技术错误、有效空数组，还是 unrelated 判决；也不能确认 51 次都是有效模型筛选。**代码缺少鉴权是已确认缺陷，历史一定收到 401 不是已确认事实。**

修复要求：

1. 从已配置端点与密钥读取配置，使用标准 Bearer 鉴权；不打印密钥。
2. HTTP/网络/鉴权/JSON 解析/缺少候选 ID/有效语义拒绝分别记录，不能都返回 `[]`。
3. 保存完整提示哈希、候选清单、原始响应、实际返回模型、响应 ID、用量、finish reason、错误种类及重试次数。
4. JSON 输出强类型检查：`supported` 必须是真正布尔值，不得用 `bool("false")` 等宽松转换；所有请求 ID 都要有明确合法结果，缺失项标技术无效/未知。
5. 每完成一题就落盘，避免进程停止后丢失全部结果。完成数拆成 planned / attempted / valid / technical_failed / not_run。
6. 固定一次技术重试上限。未通过连接和输出契约的小样本自检前，不继续批量筛选。

### 3.3 模型必须实际看到候选中心和支持上下文

当前模型提示仅显示每个原子窗口拼接文本的前 **420 字符**。原窗口包含开头语境和中心附近事实，中心往往在后方。这样即使目标 ID 在内存里，模型也可能根本没看到目标文字。

按当前代码对**全部 80 题离线重建输入**，共有 668 个候选窗口：其中 467 个中心的起始位置已经超过 420 字符，完全不可见，只有 90 个中心完整可见。高层候选为 412 个，其中 304 个中心完全不可见。这是准备输入的审计，**不是所称 51 次历史调用的响应统计**，也不是新筛选结果。逐候选偏移和代码哈希保存在 `CODEX_SCREEN_INPUT_REPLAY_20261024.json`。

必须把审计延伸到最终提示：

- 记录每个候选实际发送的事实 ID 与可见字符/区间。
- 优先保留完整目标中心及必要关系上下文，删除无关开场；禁止无条件 `text[:420]`。
- 总筛选 token 预算不足时，按统一规则减少完整候选组；不能切掉中心却仍计作“已评估该目标”。
- 若单中心过长，明确 too_long/预算回退，或提供有偏移的完整相关子句；不静默把残缺文本当完整支持。
- 模型看不到的目标、超预算未发送的候选、技术失败的调用都不能进入“语义不相关”分母。

当前模型脚本把低层与高层候选合在同一次调用，且没有 B 的覆盖说明，也没有真正生成两臂各自的选择结果。它最多是一个候选诊断实验；不能称已经完成预算匹配的 L_rel/H_rel 干预。

## 4. R1.2 的核心改造：从字段出现转为绑定的支持事实

建议新建 `F:/codex数据库memory/locomo_hierarchy_relevance_r1_2_20261024`，保留旧文件和哈希。不要重建低层正文或改 W0 时间换算。

### 4.1 用关系实例和答案值表达覆盖

查询计划区分：已知主体/参与者角色、所问关系、已知约束、未知答案位置。候选支持单元至少包含：

```text
support_atom = (
  subject_ref, participant_roles, relation,
  object_or_answer_value, event_or_context_ref,
  modality, polarity, event_time_with_grain,
  supporting_fact_ids
)
```

`support_atom` 是对实际派生事实的结构化索引，不是新增事实真值。无法确定的字段保留 unknown，引用必须存在。R1 仍只称“派生事实支持”，不升级为原文语义证明。

例：问题问 Jolene 给 Deborah 推荐哪些游戏。实体名和 recommend 在 B 出现过，不表示清单完整；每一款被支持的不同游戏值都可能是新的所问成员。问题问某次事故何时发生，B 中另一事件出现 September 不表示该事故日期已被覆盖。

必要时允许同一答案值的更清楚指代、状态或时间绑定改善证据，不强制每次增补都创造一个新名词。但同义改写和重复路径不能重复算成独立成员。

### 4.2 替换损失按支持实例评估

共同 B、前 20 个保护窗口及最终最多 24 窗口先保留。改变后 4 个窗口即可检验机制；不先扩大上下文。

对每个拟替换尾部窗口，比较：

```text
lost_support = support(victim) - support(other_selected ∪ candidate)
gain_support = support(candidate) - support(other_selected)
```

以上集合元素是绑定的关系/答案值，不是 person/time 这类类型标签。候选应满足所问关系与约束，补充有效支持或减少歧义；被删除的相关独有支持不得丢失。不能把任何一个人名命中都永久锁住尾部。

初版可由同一模型选择器给出窗口支持、相对相关性及替换 ID，程序负责来源、全局去重、保护前缀、窗口和 token 预算。模型判断仍要抽查；不用未校准的置信度作为证明。

每次原子提交后重新计算当前 `covered_fact_ids` 和支持集合，不能只做历史并集，使已经删除的事实继续被误认为覆盖。所有失败回退直接返回已保存 B 文本。

### 4.3 先去重与跳过已覆盖，再限制候选数量

1. 对完整 top-200 高层规范路由展开真实目标原子窗口。
2. 按最终窗口内容/来源去重，并记录哪些是 B 已有支持、哪些目标在 B 外。
3. 不通过旧 `no_new_slot` 过滤新答案值。允许宽松候选进入共同相关性筛选。
4. 在这个候选流中填充高层槽位，直到至多 16 个，或路由池耗尽；不能先取 16 条原路由再发现多数已被 B 覆盖。
5. L_rel 最多 64 个原子槽位，来自公共低层候选；H_rel 同上限，至少保留可用的 48 个低层槽位、至多 16 个高层发现窗口。B 的至多 24 窗口包含在公共部分。
6. 两臂同样的公共实体/关系字段、查询计划、筛选器、模型、提示、token 与调用上限。高层来源标签与层级票数不输入相关性核验器。
7. 每臂使用自己的候选池；如两臂完整提示完全相同，可共享响应。若为省钱先对候选并集做一次诊断，结果只作覆盖审计，不能冒充正式两臂算法比较。

这种操作是**查询时的去重与候选选择**，符合索引不读测试题的边界。不要根据测试题 B、金标准或历史错题，在构建阶段只保存“残差事实”。

## 6. 执行顺序、预算和验收

### 第一步：封存与确认（离线）

### 第二步：选择器正负控制（先离线，再最多 5 个有效模型自检）

准备固定的小型功能控制，至少包含：

1. **正例：同一关系的新答案值。** 例如已知游戏推荐缺失明细，或构造有真实来源的同类成员控制；即使人名/关系词已覆盖，也不能被 `no_new_slot` 自动拒绝。
2. **正例：目标在窗口后部。** 最终提示必须能看到完整目标，不能被前 420 字符截掉。
3. **正例：安全替换。** 尾部只有重复或所问关系无关支持；新候选补充明确所问值，必须能走到一次合法替换提交。
4. **负例：同人物不同事件/状态。** 仅主题相近应拒绝；计划不能冒充实际完成。
5. **技术失败控制。** 注入失败或缺失 ID，状态必须为 technical_error/invalid，不能算 unrelated。
6. **无安全替换。** 候选有价值但尾部保留独有必要支持，必须回退，不能为增加接受率硬删。

既有中心、去重、纯删除和同 group 新事实等 P0 契约继续保留。新增一次真实接受和一次真实替换的后渲染审计，确认支持实际出现在最终字符串中；字段写进列表不等于最终提示可见。预算字段使用真实 token 数，`evidence_chars` 另列 chars，不能叫 tokens。

技术和功能控制完成后，使用明确配置做**最多 5 个有效模型自检**；技术失败按预设上限停止排查，不以“无接受”继续批量花费。通过标准是连接、输出契约、目标可见及正负控制符合预期，而不是要求任意真实题有固定接受比例。

### 第三步：完成 20 题语义来源核对 + ≥40 组候选审核

可并行准备，但先完成候选输入契约。候选审核至少 40 组，按来源/接受拒绝/新答案值/同事件误配分层抽取，不用文档前 40 行聚合拒绝原因替代。每行必须有真实候选 ID、文本、问题、实际判决与审核结论。隐藏 arm、原答题正确性。

## 7. 对交接提出的四个问题直接答复

1. **是否让高层只索引低层未覆盖事实？** 不做依赖题目 B 的构建期残差数据库。允许查询时展开后跳过已呈现支持，再填充候选槽位。两层来源相同是公平比较的必要条件之一，不是无增益的证明。
2. **如何定位 B 瓶颈？** 使用 S→D→C_L/C_H→B→答题/评分的证据链，允许跨消息支持及时间计算；先审 20 题，替换当前单条金标词覆盖分类。
3. **R2 是否必要？** 目前证据不能排除，也不能确认其必要性。它还可能修复角色/指代/事件时间绑定，价值不限于某个关键词是否被摘要删除。按来源审计决定范围。
4. **是否改目标为证明无增益并封存？** 不预设正结果或负结果。先让实验具备有效干预和观测能力；若届时确实没有差异，封存当前配置即可，无需无限调参，也不能推广成高层框架无效。
