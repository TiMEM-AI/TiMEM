# R1.1 选择器与筛选输入独立复核

日期：2026-10-24。范围：只读代码、现存 P0/P1 产物，以及确定性候选输入的离线重建。未调用网络、筛选模型、答题模型或判分模型；未改动既有实验文件。新增复核文档、复现脚本和 JSON 不属于下一轮检索改造。

## 1. 可确认的结果与不可推导的结论

现存 `requests/p1` 的五组证据在 80 题上全部与 B 相同，P1 接受数为 0；这是可复核的产物事实。由此只能确认本版机制没有改变证据，不能推出“B 已覆盖所有有用事实”“选择器不是根因”或“高层同源导致无增益”。

`P1_MODEL_SCREEN.json` 实际不存在，未找到可核对的 51 次原始响应或有效判决。报告中的“51/80 完成、全部 unrelated/unsupported”应标为未核实，不应参与机制归因。

## 2. 槽位定义使新增事实难以进入

`tools/p1_groups.py:54–80` 仅记录问题中的实体词、关系词和 time/person/place/reason 类型，不记录对象值、事件 ID、时间值、列表成员或主体与关系的绑定。

例如同一实体两次参加同种活动、两个不同日期、同一人物拥有不同物品，都可能映射到完全相同的槽位集合。已有一个带年份的无关句子，也可能使 `("type", "time")` 视为已满足。槽位饱和不等于答案支持完整。

`tools/p1_groups.py:165–169` 在语义相关性判断之前，要求候选必须提供新槽位；已知实体的另一个相关事件可能在这里全部被拒绝。`201–212` 又先遍历全部低层候选，再考虑上层，低层优先占据少量粗槽位。因此 `no_new_slot` 的三四万次计数不能视为三四万次独立的正确排除。

## 3. 替换保护仍使大部分尾部不可替换

`tools/p1_groups.py:134–137` 从当前选择集累计 `covered_slots`。`183–190` 再用当前某个窗口独有事实构造 `victim_slots`，并在 `victim_slots & covered_slots` 非空时拒绝替换。这些槽位本来就来自当前集合，其交集非空几乎等价于“该尾部出现过任何问题相关词/类型”。

应改为评估移除该组后的问题支持损失：从其余组重新计算真正得到支持的事件/属性/桥接步骤，检查候选是否补回损失，不能以受害窗口槽位属于整个当前集合为拒绝理由。

此外，替换后 `covered_slots |= slots`（196 行）没有移除已经消失的槽位；若以后成功替换，这会产生过期覆盖状态。146–149 行去重后又无条件插回已覆盖中心，也会使重复中心继续作为候选进入检查。

## 4. “B 恒为 24”与产物不符

`P0_EVIDENCE_AUDIT.json` 和 P1 请求实际均为：79 题 24 窗口，1 题 1 窗口；合计 1,897。报告中的“恒为 24”应更正。

24 个窗口只是输出截断结果，不是完整事实库。根复核 `CODEX_HANDOFF_AUDIT_20261024.json` 按相同 `upper_pool()` 计算显示：79/80 题的 top-200 上层路径仍有 B 外目标，唯一目标事实数中位 151，范围 0–180。它们尚未经相关性审核，不能宣称都是有用事实，但足以否定“看见 6–11 个候选即说明全索引只剩这么多”的推导。

`tools/p1_model_screen.py:81–82` 先将 lower 截为 24、upper 截为 16，随后 `92–100` 才过滤 B 已覆盖目标。候选少至少部分来自先截后滤及每条路径只展开第一个 B 外目标，而非已证明的候选池耗尽。

## 5. 模型输入把多数目标事实截掉

可复现脚本：`tools/codex_replay_screen_inputs.py`。

输出：`CODEX_SCREEN_INPUT_REPLAY_20261024.json`，含源代码 SHA、逐题候选 ID、完整窗口长度、中心起始偏移和可见前缀 SHA。该脚本只重建当前代码对全部 80 题准备的候选输入，**不是所称 51 次历史调用的响应统计**。

`tools/p1_model_screen.py:45–49` 对每个候选仅保留 `text[:420]`。而 `grounded.py:175–179` 的窗口常为开场两条加中心前后文，命中中心经常出现在后半段。

| 当前代码离线重建的 80 题 | 低层候选 | 上层候选 | 合计 |
|---|---:|---:|---:|
| 候选窗口 | 256 | 412 | 668 |
| 中心事实完整呈现 | 50 | 40 | 90 |
| 中心事实开头位于前 420 字符内 | 93 | 108 | 201 |
| 中心事实起点已超过 420，完全不可见 | 163 | 304 | 467 |
| 整个窗口被截断 | 239 | 403 | 642 |

每题候选数为 1–16，中位 8。上述 467 个窗口即使得到有效模型响应，也可能是在审核开场或邻句，而非目标事实。下一轮必须保证中心及必要指代上下文完整呈现，按 token 预算分配上下文，记录模型实际所见文本，再谈相关性结论。

## 6. 模型请求和日志不能支撑“有效的 0 接受”

`tools/p1_model_screen.py:28–30` 虽读取 KEY，但 `53–55` 的 `client.post()` 没有传认证 headers，`75` 也没有在客户端设置。`60–62` 将所有异常重试后转成 `[]`，与模型合法返回空列表混为一类。随后 `109–115` 缺失判决会记为 unknown，不能被描述为 unrelated/unsupported。

代码只在全部循环结束后（123–125 行）写汇总，没有逐题持久化原始响应、HTTP 状态、解析状态、响应 ID 或错误。不能从打印的 `accepted=0` 证明调用成功或判决有效。

下一轮先完成 1–2 题连通及 JSON schema 校验。错误、超时、解析失败、ID 缺失分别记为失败，不记作拒绝；每题落盘后继续。所有声称完成的筛选题都必须有可追溯的有效响应。

## 7. 五组消融与预算尚不成立

`tools/p1_groups.py:237–240` 中 H_fold 与 H_rel 完全是同一个 `select()` 调用，实际 80/80 证据相同。H_raw 也使用这个共享规则，未实现注释所称 raw/fold 组的 legacy 选择规则。因此不能将这五个名字解释为五个独立机制。

低层候选遍历上限 400，额外上层路径上限 200；本轮记录的 L_rel 约 29,720 次候选判断，H_rel 约 40,996 次。未落实先前规划的固定候选槽位和公共重排预算。模型筛选脚本仅产生一个混合候选审核列表，没有落盘独立的 L/H 可达性掩码、最终选择、实际答题输入与等预算比较，不能称其已完成两臂预算匹配实验。

建议用两组核心对照加可选消融：L 仅有低层候选，H 有低层与高层导航候选；同一事实库、相同候选上限/完整文本 token 预算、相同选择器调用预算、相同最终证据 token 预算。若共享一次并集筛选结果，必须保留各臂可达掩码，并承认并集上下文是共同筛选资源；用于预算匹配结论时优先分别筛选、按完整提示缓存，避免上层候选改变低层筛选上下文。

## 8. P0 尚需补充的非空契约验证

P0 没有接受任何上层窗口，故 `target_missing=0` 只是未触发路径的结果。`tools/p0_audit.py:134–136` 检查中心 ID 是否属于选中集合，没有对真正渲染文本逐一核验。`base_tokens/h_tokens`（152 行）实际是字符数，也不能直接当 token 使用。

应增加确定性构造的非空测试：可接受新增、可接受替换、拒绝后完全回滚、中心在组中后部、同观察时间、中心与关键上下文完整渲染、预算裁剪后仍有中心。测试需从最终真实输入验证 ID→文本/span 映射，并从最终集合重算 covered 状态。P1 也尚未接入 P0 的直接日期保护（当前 `select` 无 guard），后续激活机制时需明确是否保留，并在两臂一致处理。

## 建议交接顺序

1. 先将不可追溯的模型筛选结论与“B 已饱和”归因标为未证实，保留原报告供审计。
2. 离线修复候选预截断、中心呈现、槽位与替换判据，完成非空契约测试。
3. 完成可追溯的小样本相关性/桥接人工核验，再运行有效模型筛选；失败与拒绝分开。
4. 冻结机制及预算对照，达到真正证据改变和相关性条件后，再运行新的 smoke 与配对全量；当前未产生新分数。

高层与低层同源是预期结构：高层的价值应是帮助找到低层单独检索漏掉、但同一事实库中确有支持的内容，或用更低预算组织相同支持。没有必要以“不同源事实”作为高层有效性的前提，也不应按测试题/金标将未召回事实专门写入高层。
