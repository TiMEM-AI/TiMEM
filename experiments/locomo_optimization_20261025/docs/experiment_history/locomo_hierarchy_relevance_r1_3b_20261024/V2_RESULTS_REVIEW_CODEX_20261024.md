- state.json 有 18 个 done，但这 18 个条目的 prompt_sha **全部不等于**对应当前 requests 文件的 prompt_sha。

- 最新 READINESS_V2 报告明确只进行了离线重建，因此目前没有最新版本的筛选响应和端到端评分。
- r13b_run.py 第 55 行仅以 qid:arm 是否在 state.done 决定跳过，未校验 prompt_sha。直接重跑将跳过这 18 个新请求。
- r13b_fix.py 从 state 读取 selected/removed，再按当前 requests 的 c1…c12 解释，未核对请求 hash。候选池已变化后直接复用旧状态，会把旧计划解释成新候选。

## 实际 runner 仍存的问题

当前 r13b_run.py 第 60–62 行仍分别含 [:9000]、[:6000]、[:12000]，与“输入截断已移除”的文档说法不一致。仅有离线证据文件完整，不能证明发送给筛选模型的内容完整。

此外，runner 第 17/78 行仍调用 r13b_prepare.apply_plan；r13b_fix.py 的 apply_plan_fixed 用于离线重建。全量入口应明确调用经过修复的同一应用函数，防止测试函数与生产函数分叉。

## 最小执行要求

1. 最新版使用新输出目录或完整请求 hash 隔离旧 state/responses/evidence/answers；缓存键包含题目、完整输入、模型和提示版本。
2. 消除 runner 的三处截断并记录实际发送 prompt 的 hash；交换应用使用通过契约验证的函数。
3. 用离线生产路径回归确认新请求不会被旧 done 跳过、交换计划准确应用、guard 任务写明回退 B、最终证据与计划一致。同证据可共享答题和判分，但共享键须包含题目。
4. 答题记录保存证据 hash、题目/提示 hash、模型、原始 judge 输出及错误类型。旧成绩保留为历史，不改写成 V2 成绩。
5. 上述生产路径回归与版本一致性通过后即可冻结开始 861 题；不要求再做 20/80 题调分，也不要求小样本先出现准确率正收益。若选择重跑 20 题，应对全部 18 个 planned 任务重新筛选，并保留为独立 V2 记录。

## 全量缓存注意

r13b_answer.py 的全局 cache 仅以 evidence 文本为键。本次 20 题不存在跨题相同证据，因此未发现实际误复用；全量中相同证据可能服务不同问题，缓存键必须纳入 qid / 完整问题与模型设置。
