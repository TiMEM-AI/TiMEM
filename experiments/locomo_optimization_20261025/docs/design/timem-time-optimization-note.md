# TiMEM 时间类题目优化参考（可同步给其他数据集负责人）

> 适用：AML 文本赛道，任何跑 TiMEM 分支的数据集。
> 结论先行：**时间类题目的最大失分原因是"记忆里没有绝对日期"，不是检索不到。**
> 实测时间类准确率 20% → 50~60%，总分 67.8% → 72~82%。

---

## 一、问题现象

以 LoCoMo-Refined（conv-26，20 道时间题）为例，优化前只对 4 道（20%）。

错误答案 **100% 是同一个模式**：金标是绝对日期，模型答相对表达。

| 金标 | 模型答案 |
|---|---|
| May 20, 2023 | Last Saturday |
| June 2023 | Next month |
| From May 29, 2023 to June 4, 2023 | Last week |

而检索回来的记忆长这样：

```text
Caroline went to a LGBTQ support group yesterday and found the transgender stories inspiring...
```

**没有日期。** 模型即使想换算也无从下手。

---

## 二、根因（两层）

### 1. 日期在传输中丢了

AML 的 `Add` 契约里 `messages[].timestamp` 是**可选**字段。实测本地评测框架**有**传（LoCoMo 的 `session_N_date_time` 会转成毫秒时间戳，419/419 条都带），但 TiMEM 的记忆生成只吃 `content` 文本，**把 timestamp 忽略了**。

> 先确认你们的数据集：`add` 请求里有没有 `timestamp`。没有的话这条改动收益有限，得从别处找锚点。

### 2. 模型会把日期"洗掉"

即使把 `[2023-05-08]` 拼进提示词，L1 生成模型的输出依然会丢掉它（实测提示词里有、结果里没有）。所以**不能依赖模型保留日期**。

---

## 三、两个改动

### 改动 A：时间戳注入（喂给生成模型）

在 `/aml/add` 里，把每条消息按 timestamp 改写为 `[YYYY-MM-DD] 原文`，再交给记忆生成。

```python
# server/time_anchor.py::stamp_messages
new_message["content"] = f"[{date_text}] {content}"
```

### 改动 B：确定性后处理（关键，不依赖模型）

L1/L2 落库后，用 `time_window_start` 给内容加日期前缀，**并把相对时间解析成绝对日期**：

```text
改前：Caroline went to a support group yesterday and found...
改后：[2023-05-08] Caroline went to a support group yesterday (2023-05-07) and found...
```

覆盖的模式：

| 表达 | 解析为 |
|---|---|
| yesterday / last night | 锚点 − 1 天 |
| today | 锚点当天 |
| last <星期几> | 锚点前最近的该星期几 |
| last week | 上一个 ISO 周的周一到周日 |
| last weekend | 上周六到周日 |
| last / this / next month | 具体年月 |
| N days ago | 锚点 − N 天 |

**幂等**：已带 `(日期)` 的短语和已带 `[日期]` 前缀的内容不会重复处理（重复执行更新 0 行）。

代码位置：`server/time_anchor.py`，在 `/aml/add` 成功后调用一次。

## 四、效果

| 版本 | 总分 | 时间类 |
|---|---|---|
| 基线 | 59/87 = 67.8% | 4/20 = 20% |
| + 日期锚点 | 62/87 = 71.3% | 6/20 = 30% |
| + 相对时间解析 | 63/87 = 72.4% | 10/20 = 50% |
| 同配置重跑 | 71/87 = 81.6% | 12/20 = 60% |

**时间类四次单调上升（20%→30%→50%→60%），这条改动的方向是确定的。**

### 稳定基线（生成温度改为 0 后，同配置连跑 3 次）

| 运行 | 总分 |
|---|---|
| run5 | 69/87 = 79.3% |
| run6 | 70/87 = 80.5% |
| **run7** | **73/87 = 83.9%** |
| **中位数** | **80.5%**（均值 81.2%，极差 79.3–83.9） |

分类别（三次均值）：

| 类别 | 准确率 | 三次明细 |
|---|---|---|
| 4 单跳 | **91%** | 45 / 45 / 46 |
| 3 推理 | **95%** | 7 / 7 / 6 |
| 1 多跳 | **67%** | 7 / 7 / 6 |
| 2 时间 | **60%** | 10 / 11 / 15 |

> 温度归零后极差从 9.2 分缩到 **4.6 分**，说明之前的大幅波动主要来自生成随机性。
> 对比时请用中位数，不要用单次。

## 五、三个必须注意的坑

### 坑 1：噪声很大，小分差不可信

同一套配置两次跑出 **72.4% 和 81.6%**（差 9 分）。原因：

```yaml
config/settings.yaml
  llm.dialogue_system.temperature: 0.8   # 记忆生成是随机的
```

答题和判分已经是 `temperature=0`，但**记忆生成不是**。所以每次跑 L1 措辞都不同 → 检索排序不同 → 答案不同。

**建议全组统一把生成温度设成 0**，否则 87 题规模下的对比没有意义。每次比较至少要跑 3 次取中位数，或用更大的卷（861 题）。

### 坑 2：记忆变长，可能挤占其他题

加日期后每条记忆多了 `[日期]` 和 `(绝对日期)`。100 条证据拼进 prompt 会占更多 token，实测单跳类有小幅波动（88% → 82~90%）。

如果发现其他类别掉分，可以只对**含相对时间的句子**加 `(日期)`，前缀 `[日期]` 保留（成本低）。

### 坑 3：`created_at` 不是写入时间

TiMEM 把 `created_at` 存成**会话时间**（LoCoMo 是 2023 年）。想"只处理刚写入的行"不能用 `created_at >= now()`，会一条都匹配不到。用 `time_window_start` 做锚点，用幂等条件（是否已带前缀）代替时间窗口。

## 六、顺带提醒的两条通用问题（换个数据集也会中）

1. **跨 user_id 泄漏**：语义检索那一路原本只按 `character_ids` 过滤，没带 `user_id`；BM25 那路的 adapter 链路也没透传。实测 A 用户的检索结果里出现了 B 用户的记忆。
   建议：在 `/aml/search` 出口加一道硬校验——按 id 回查 `core_memories.user_id`，不匹配直接丢弃，**查询失败时返回空**（fail closed）。

2. **L2 重复汇总**：同一 session 的 L2 会出现多条，且子节点集合完全相同（实测 3 条 L1 → 3 条 L2，每条都挂同样 3 个 L1）。因为 L2 只按时间窗判重，不按"覆盖了哪些 L1"。
   建议：L2 用 `hash(排序后的 child_ids)` 做幂等键，已存在就跳过。实测加上后 3 条 L1 → 1 条 L2。
